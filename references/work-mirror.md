# Work mirror

## Classify before correcting

| Problem layer | Diagnostic question | Typical next best action |
|---|---|---|
| Goal | Is the intended outcome or definition of done unclear? | Restate one measurable outcome. |
| Information | Is a decision being made without a necessary fact? | Gather the cheapest decisive fact. |
| Decision | Are options present but tradeoffs or reversibility unclear? | Separate reversible from irreversible choices. |
| Execution | Is the next action known but repeatedly not taken? | Make the smallest external commitment. |
| Method | Is effort repeating without changing the tested assumption? | Predict, run a falsifying check, and reconcile. |
| Resource | Is scope larger than available time, money, skill, or permission? | Reduce scope or obtain the missing resource. |
| Environment | Is the workflow or context creating avoidable friction? | Remove one concrete blocker. |
| Evaluation | Is progress measured by a proxy instead of the real outcome? | Replace the proxy with user or result evidence. |
| Bias | Is the user considering only supporting evidence or sunk cost? | Seek one counterexample or stopping condition. |

Do not collapse every stalled task into procrastination, fear, or perfectionism.

## Intervention policy

- Intervene immediately for direct goal contradiction, repeated failed action, destructive or high-impact omission, or evidence-free certainty with material consequences.
- At a natural checkpoint, intervene when two independent observations support the same pattern.
- Stay silent for ordinary preferences, harmless inefficiency, or a single ambiguous signal.
- Allow at most one unsolicited checkpoint per task stage. Do not repeat it without new evidence.
- For a destructive or irreversible action, require both the exact target and a recovery path that has been tested. The existence of an untested backup is not enough.

## Correction card

Use the contract in `SKILL.md`. Quote the smallest sufficient evidence. Give one next action, not a list. If the action depends on code, design, finance, law, medicine, or another specialist domain, route to an appropriate skill or reliable source instead of improvising expertise.

Prefer an internal next action using evidence and actors already in scope. Do not invent a team, stakeholder, customer, or other unsupported actor. If the user explicitly asks to design a mandatory external-validation policy, follow that request within applicable domain and safety constraints. Otherwise, when external validation is already an explicit work goal, offer at most one minimal optional test; do not turn user testing or feedback collection into a mandatory gate.

## Verify the correction

Before the action, state a discriminating prediction. After evidence arrives, compare prediction with result and keep, revise, or discard the diagnosis. A compelling explanation without an outcome check is unfinished.

Do not invent a sample size, deadline, price, conversion threshold, or payment mechanism when the context does not establish one. Use the smallest feasible test, label suggested parameters as assumptions, and defer domain-specific validation design to the relevant skill or evidence.

## User controls

Honor immediately: stop correcting, skip this, this is temporary, do not remember this, only high-risk reminders, or resume correction. A user correction overrides the prior pattern; acknowledge and withdraw it instead of defending it.
